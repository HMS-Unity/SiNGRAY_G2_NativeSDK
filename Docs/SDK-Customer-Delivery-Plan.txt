SiNGRAY Native SDK customer delivery plan
Updated: 2026-11-02
Repository: SiNGRAY G2 Native SDK; target branch: dev/4.2

Delivery boundaries
This repository delivers a customer SDK. Test APKs demonstrate individual features; they do not establish complete customer integration readiness.
Keep three work areas distinct: required SDK/runtime and customer Editor setup assets; optional integration samples; internal diagnostics and validation tools.
Application-specific medical, AR Engine and spatial-alignment development stays in separate application projects. Do not migrate application history into this repository.
Preserve public interfaces, enum values, serialized references, asset GUIDs, required Resources paths and existing standalone/BaseScene/Hub layouts.
Do not rebuild the Hub or introduce a new distribution format as incidental cleanup.

Implemented sample work
- CameraDemo: neutral sample naming, four fisheye channels, independent channel stop, RGB resolution switching and horizontal ToF preview mirroring.
- RGBD: complete RgbdDemo prefab, retained XvRgbdDemo compatibility type, existing host previews/services and selected-pixel/world-point behavior; frame validity and shared stream ownership.
- ToF point cloud: bounded refresh storage, lifecycle handling and distance colors; original density, particle size and API retained. Point-cloud sample renaming was not performed.
- MRVideoCapture: complete configured prefab, existing host layouts, shared preview/record/stream occupancy, real-frame gates, capture cancellation and JPG worker waiting.
- SpatialMap: complete prefab, original environment/object references, serialized content format, save/load/reset operation gate, callback/path correlation and nonempty-file checks; reusable feature particles.
- SpatialMesh: complete prefab, shared reconstruction occupancy, latest update per map ID, Mesh/material reuse, explicit destruction and large-mesh index handling.
- TagRecognizer: neutral prefab/component with legacy compatibility, original host defaults, shared native sessions/RGB occupancy, cancellable readiness, retained fisheye worker and bounded result storage.
- StaticGesture: neutral prefab/component with legacy compatibility, corrected mappings for OpenHand/Call/Rock/Thumb/Pinch, independent frame snapshots, first-frame held state and safe lifecycle reset.
Standalone scenes, legacy menu scenes and Hub modules retain their own layouts and existing services; newly embedded service duplicates are disabled where the host supplies them.
The Hub generator reuses configured modules for RGBD, MRVideoCapture, SpatialMap, SpatialMesh, TagRecognizer and StaticGesture. It was not run to reconstruct the Hub.
STM/Joystick removal and OCR sample cleanup were previously requested. Eye-tracking deletions already staged in the source checkout are excluded from this publication; preserve the remote eye-tracking implementation and required API/Editor entries.
PlaneDetection was skipped at the user's request; its SDK capability was not deleted. Keyboard, MRTK2, ordinary MediaRecorder, RTSP and SystemSetting have not received equivalent complete sample consolidation in this round.

Known issues and limits
- SpatialMap previously stalled in native pose locks during reset. Managed operation guards and a successful user session do not prove the native root cause is eliminated.
- Native RGB recognizer logging was observed while the managed TagRecognizer mode was fisheye. Stop ordering/callback draining requires further correlation; no definitive native leak diagnosis was established.
- Historical startup XvXREye.UpdateStereoValues null-reference reports remain recorded.
- Two disabled measurement-line objects in the standalone TagRecognizer scene already have missing scripts. Preserve their objects/references; this round did not restore application code or silently delete them.
- Point-cloud start/stop showed a short pause; main-thread ASC writing and broader capture cleanup remain separate follow-ups.
- Long-run memory, every mode/size transition, exit/reentry and all cross-module combinations were not captured in every device session.
- StaticGesture validity uses the existing provider's tracking flags. It does not independently establish native callback freshness or change the global hand tracker.
- RGB callback ABI has no session token; very late callbacks after a later start require supplier/device verification.

Remaining customer delivery work
B1: finish feature/entry/resource dependency inventory, including property-level host differences.
B2: continue per-module consolidation only when requested; preserve host overrides.
B3: review legacy variants and BaseScene retirement only after all generator dependencies and equivalent entries are verified.
A1: document customer API boundaries, native buffer lifetime, coordinate/timestamp conventions and required initialization assets.
A2: validate native reset synchronization, concurrent consumers, teardown, pause/resume and supported hardware/firmware combinations.
C1: classify internal tools separately from required customer Editor setup and reproducible validation.
D1: define distribution contents, dependencies/licenses and test import/build/init in a clean customer project. No distribution format has been frozen or official Release published.

2026-11-02 KeyInput follow-up
The previous minimum KeyInput scene was an OnGUI simulation/log sample, not a consolidated XR demo. It was not part of the earlier completed sample list.
By explicit user selection, it is now a standard SDK XR scene with an Editor-visible world-space panel and a reusable KeyInputDemo prefab. The scene moved to KeyInput/Scenes with its GUID retained; the old OnGUI component remains available separately.
The panel uses existing MRTK press controls and shared SDK input APIs. Four default keys and rotary simulation are supported; two additional semantic-key rows require custom profiles. No raw codes were invented.
Validated 23 core assertions, 15 runtime panel/lifecycle assertions and 27 Android assemblies; inspected an actual Editor render. Physical hardware behavior remains pending. No device installation/launch was performed.
The standalone scene includes the existing native XR host; the content prefab is intended for an already initialized SDK scene. Hub layout and registration were not changed.
